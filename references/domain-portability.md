# 跨领域移植与扩展性

本文件说明：为什么五要素框架能在不同领域通用，为什么「默认值」需要随领域变化，以及你（或本 Skill 的未来版本）如何新增一个领域。

## 为什么框架稳定

五要素对应人类委托任务的通用信息结构，与领域无关：

- **角色** = 谁来做（任何任务都需要一个执行者视角）
- **背景** = 在什么条件下做（任何任务都有约束条件）
- **目标** = 要什么（任何委托都有交付物）
- **约束** = 不能怎样（任何任务都有红线）
- **格式** = 以什么形态收（任何产出都要可被消费）

因此引擎本身不需要为领域改写，它被设计成「稳定骨架」。

## 为什么默认值会变

框架稳定，但每个领域的「专家知识库、风险面、交付形态」不同，体现在四类默认值：

- **角色原型**：营销要「操盘手视角」，代码要「资深工程师 + 代码审查者」，法律要「严谨风控视角」。
- **背景清单**：营销关心竞争环境与筹码；代码关心技术栈、规模与兼容性；法律关心 jurisdiction 与证据链。
- **默认约束**：营销忌黑话，代码忌引入未声明依赖，法律忌给出确定性法律结论。
- **格式选项**：营销常用表格 + 钩子清单；代码常用带签名的代码块 + 测试；法律常用条款式分层。

## 领域档案契约（扩展点）

每个领域档案是一个固定字段的 Markdown 文件，置于 `references/domain-profiles/`。引擎在运行时按用户领域读取对应档案。契约字段如下，新增领域时逐项填写即可，**无需改动引擎或脚本**：

```
## 角色原型
<该领域默认的身份锚点 + 评判标准>

## 背景清单
- <该领域应追问的真实条件 1>
- <该领域应追问的真实条件 2>

## 默认约束
1. <该领域常见禁用项>
2. <该领域资源/合规上限>

## 格式选项
- <推荐呈现形态 1>
- <推荐呈现形态 2>

## 移植要点
<该领域套用五要素时特有的坑与调整>

## 示例
<一个填好的五要素片段>
```

## 如何新增一个领域（三步）

1. 在 `references/domain-profiles/` 复制任一现有档案，改名为 `<your-domain>.md`。
2. 按上面契约填写六个字段；只写结构建议，不编造领域事实。
3. 在 `SKILL.md` 第 3 步的路由列表里补一行指向新档案。

引擎会自动识别并加载，不需要改 `../scripts/build_prompt.py`，也不需要改核心流程。这是本 Skill 的可扩展性落点。

## 当前内置领域

营销、软件工程、学术写作、法律、数据分析、产品。未覆盖的领域走「其它领域」分支，按契约临时生成**通用骨架**（即各 `domain-profiles/*.md` 中「模板骨架（可一键套用）」段的通用版），并标注「未加载领域默认值」，供 F2 模板套用兜底；骨架只给结构占位符，不预填任何领域事实或数据。未覆盖领域同样触发 **F4 领域权威溯源**：依 `authoritative-sourcing.md` 的「通用权威原型」（对应国家主管部门官网 + 公认标准 / 学术机构 + 权威行业组织）检索 3 个来源，并标注「未加载领域默认值，来源为通用权威渠道」。
